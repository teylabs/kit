# Starter blueprint delivery increment

Opinionated versioned application contract and public Mod scaffold pack. A/B and C/D are local synthetic release fixtures, not published versions. Runtime tenancy/membership/settings stay in maintained packages and host bindings.

The `starter-foundation` scaffold uses public released Mod APIs. Preview with `starter:foundation --dry-run --json`; then generate explicitly with `--no-interaction`. A/B generate one policy file. C/D add a separately owned defaults file for the two-file upgrade proof. It does not establish a bootable/authenticated application, persisted ownership, upgrade/recovery, browser or product-MCP acceptance.

Generated paths and host-owned branding/domain/configuration/data are distinct in the blueprint. The source reference content-addresses the manifest plus all resource bytes; baseline resources remain available for comparison. Generic lifecycle machinery is a separate reviewed Mod requirement. No private Mod APIs, forced overwrites, semantic merging, package publication or automatic production updates.

The initial recipe fixes the member name and ungrouped placement. Alternate command names cannot widen ownership. Only the Laravel layout with all declared paths and classes is supported; incompatible layouts refuse before generation.

The original A/B resource bytes and source references are pinned and retained. New C/D fixtures represent logical consumer baseline/target versions 0.3.0/0.4.0; both policy and defaults resources change. Each member has a fixed class/path, and every member validates the entire placement set before generation starts. Defaults occupy their own explicit folder so released Mod reverse-mapping remains unambiguous. Ordinary generation preserves existing customised output; it is not the persistent upgrade protocol.

Run `php tests/ScaffoldCheck.php <autoload.php> C` (also A/B/D) against a public Laravel13/Mod0.7.2 install. The optional `misplace-defaults` argument checks that a mismatched second member refuses before writing the first. Each run creates a distinct synthetic filesystem fixture, not a real application consumer or an installed ownership record.

The experimental lifecycle adapter composes only public Mod `Artifact`, `Checkout`, `FilePlan` and `Maintenance` APIs. **Released Mod 0.7.2 explicitly refuses lifecycle; it still supports the scaffold.** Local proof requires an explicit `local-experimental` descriptor with an exact 40-character source ref and a trusted verifier returning that exact ref. The verifier must check the actual loaded API paths and source bytes against the selected immutable source, not merely echo the descriptor. False, true, mismatched refs and exceptions refuse before delivery. There is no published maintenance dependency or release claim.

Bind `LifecycleHost` explicitly to application-owned code for `starter:maintain`. It supplies the app ID, frontend bindings, actual named input files, verified `Lifecycle`, and a real operation/tenant acceptance closure. There is no default success callback. Required input IDs are `verification-policy`, `verification-code`, `dependency-lock`, `host-config`, `host-binding`, `host-operations`, plus `experimental-mod-source` for an overlay. These must name the actual policy, registered implementation, lock, configuration and binding files; include additional relevant package/verifier implementation inputs. The operation closure must be declared in the file named by host-operations; reflection rejects an unbound implementation before delivery. Delegated implementation and package/verifier inputs must also be declared. A marker containing a ref does not prove source identity. The trusted verifier and package checks run before effects and again before recording, including after the host operation callback. Host code cannot replace package dependency/resource checks.

Preview with `starter:maintain plan --target=C`. Review its plan identity before `starter:maintain apply --target=C --intent=<stable-intent> --expected-plan=<identity> --exclusive-checkout`. Upgrade with `--original=C --target=D`; retry an interrupted exact intent with `starter:maintain resume` and the same original/target/intent. Every refusal or noncompletion exits nonzero, including conflicts, failed verification and unresolved orphan candidates. Completed cold retries use the authoritative receipt without rerunning host callbacks. No force, semantic merge, migration execution or orphan deletion exists.

The artifact's inert metadata contains the pinned blueprint source, complete manifest and truthful empty applied-migration IDs. Requirements, migration declarations, exceptions and host ownership are provenance, not execution evidence. The generic Mod installed record remains the sole version authority, committed last. Overlay provenance is included in artifact metadata and results; its actual host verification inputs are also bound into that record's input fingerprints. Changing the engine source requires an explicit reviewed baseline transition; a changed descriptor cannot reuse an old completed intent. All paths require an exclusively owned checkout. Advisory locking cannot protect against arbitrary editors; preserve/refuse conflicts and unresolved recovery files.
